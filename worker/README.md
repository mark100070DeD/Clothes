# Cloudflare Worker: поиск скидок и мгновенный `/start`

## Зачем

Раньше скидки искал часовой прогон на GitHub Actions, и новая уценка доходила до
человека с задержкой до часа. Теперь ищет сам Worker: крон будит его раз в
минуту, задержка упала до нескольких минут.

```
крон раз в минуту
   ├─ минуты 0,1,2,3 пятиминутки → 2 живые страницы Пумы   (скорость, круг 15 мин)
   └─ минута 4                   → 2 страницы индекса      (полнота,  круг 15 мин)
                    ↓
            новый SKU или цена ниже запомненной в KV
                    ↓
            страница товара → ЦЕНА, размеры, цвет  ← истина берётся здесь
                    ↓
            карточка в Telegram + seen в KV + витрина для /start

Telegram --webhook--> Worker --> витрина из уже отправленных карточек (KV)
```

## Два источника и почему их два

| источник | что даёт | чем плох |
|---|---|---|
| поисковый индекс Пумы (Klevu) | весь каталог 5183 товара за 6 запросов и 1.26 МБ; покрытие распродажи 100% (проверено: 591 из 591) | **для свежих уценок бесполезен**: из шести скидок, найденных 25.09.2026, он не знал ни одной даже через 40 минут |
| живые страницы списка | настоящие цены прямо сейчас | 24 страницы по ~950 КБ, часто не походишь |

Замер 25.09.2026, два независимых: из 89 сверенных товаров индекс разошёлся с
сайтом на двух, и **оба раза живой сайт был дешевле**. А из шести уценок,
пойманных в тот же день, индекс через 40 минут не знал **ни одной** — все шесть
нашло окно живых страниц.

Отсюда распределение сил: **скорость даёт окно живых страниц**, индексу
оставлена полнота, а **цена в карточке всегда берётся со страницы товара** и
никогда из индекса.

## Что внутри

| Файл | Что делает |
|---|---|
| `src/index.js` | webhook, `/start`, служебные `/subs` и `/state`, крон |
| `src/sweep.js` | один тик обхода: расписание, отбор, проверка, отправка |
| `src/klevu.js` | каталог из поискового индекса. Перенос `puma/klevu.py` |
| `src/puma.js` | живые страницы: цены, размеры, цвет. Разбор отказов 403/429 |
| `src/state.js` | состояние в KV: `seen`, курсор, витрина, отпечаток каталога |
| `src/telegram.js` | отправка, получатели, тревоги не чаще раза в сутки |
| `src/caption.js` | подпись карточки — перенос `puma/messages.py` |
| `test/` | `node --test`, 26 проверок |

## Переменные окружения

Задаются **только в Cloudflare**, в коде их нет — репозиторий публичный.

| Переменная | Что это |
|---|---|
| `BOT_TOKEN` | токен от @BotFather |
| `CHAT_ID` | твой chat id: получаешь скидки и все тревоги |
| `WEBHOOK_SECRET` | любая длинная случайная строка, придумываешь сам |
| `SUBS_TOKEN` | пароль к `GET /subs` и `GET /state`; такой же в секретах GitHub |
| `START_ITEMS` | сколько карточек показывать по `/start`, по умолчанию 5 |
| `LISTING_PAGES` | живых страниц Пумы за тик, по умолчанию 2. **Главная ручка скорости** |
| `SWEEP_PAGES` | страниц индекса за тик, по умолчанию 2. **Ручка на случай CPU** |
| `MIN_DISCOUNT` | не слать скидки меньше N%, по умолчанию 0 |

`LISTING_PAGES`, `SWEEP_PAGES` и `MIN_DISCOUNT` меняются кнопкой в панели
Cloudflare **без деплоя** — самый быстрый способ что-то починить, в том числе
с телефона.

**Про `LISTING_PAGES`.** Скорость бота определяется тем, как быстро он обходит
24 страницы распродажи: `2` даёт круг за 15 минут и ~2300 запросов к Пуме в
сутки, `1` — круг за 30 минут и вдвое меньше запросов. Если Пума начнёт
отвечать 403 или 429 — это первое, что надо снизить.

## Развёртывание

```
cd worker
node --test                        # прогнать тесты
npx wrangler login                 # откроет браузер
npx wrangler deploy --keep-vars    # выложит Worker и напечатает адрес
```

`--keep-vars` обязателен. Переменные заданы в панели и в конфиг не вынесены
(репозиторий публичный) — обычный `deploy` стёр бы их.

Секреты (каждая команда спросит значение и не покажет его):

```
npx wrangler secret put BOT_TOKEN
npx wrangler secret put CHAT_ID
npx wrangler secret put WEBHOOK_SECRET
npx wrangler secret put SUBS_TOKEN
```

Один раз зарегистрировать webhook:

```
https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=<АДРЕС_WORKER>&secret_token=<СЕКРЕТ>&allowed_updates=["message"]
```

Проверка: открыть адрес Worker обычным GET — отдаст JSON с `last_sweep_ts` и
размером витрины.

## Разовый шаг при переезде: перенести память

У старого бота в `data/puma.db` лежат 555 запомненных цен — отметки «это уже
отправлено». Их надо отдать Worker'у, иначе он стартует с пустой памятью: сутки
молча запоминает каталог, и всё это время новые скидки не приходят.

```
python -m tools.push_seen        # или двойной клик scripts/push-seen.bat
```

Нужны `WORKER_URL` и `SUBS_TOKEN` в `.env`. Повторный запуск безопасен: Worker
сливает память, а не перезаписывает.

Сразу после переноса, на ближайшей минуте, бот пришлёт **пять карточек с самыми
крупными скидками** — чтобы было видно, что он работает, и чтобы наполнилась
витрина для `/start`. Это разовый показ, второй раз он не повторится.

# Что делать, когда сломалось

Симптом → команда. Держать под рукой.

### Бот замолчал, сообщений нет

```
cd worker
npx wrangler tail          # живой поток логов, видно причину
```
Открыть адрес Worker в браузере: если `last_sweep_ts` старый — крон не
срабатывает или тик падает. Логи скажут, что именно.

### После деплоя стало хуже

```
npx wrangler rollback
```
Возвращает предыдущую версию за секунды. **Состояние при этом не теряется** —
`seen` лежит в KV, а не в коде, так что дублей после отката не будет.

### В логах «Exceeded CPU limit»

Поставить в панели Cloudflare `SWEEP_PAGES = 1`. Деплой не нужен, действует со
следующей минуты. Круг каталога станет 10 минут вместо 5 — медленнее, но живо.

### Завалило карточками

Поднять `MIN_DISCOUNT` в панели, например до 30. Тоже без деплоя.

### Пришло «Puma ответила 403»

Бот сам остановил запросы к сайту на сутки — это правильное поведение, **не
надо перезапускать его вручную**. Долбить забаненным клиентом только хуже.
Через сутки он попробует снова. Если повторится — снизить частоту: `SWEEP_PAGES`
поменьше и реже трогать живые страницы.

### Пришло «индекс не меняется N часов»

Klevu застрял. Скидки продолжают ловиться окном живых страниц, просто медленнее.
Само чинится, когда индекс оживёт. Если висит сутками — смотреть, не сменился ли
формат ответа: `src/klevu.js`, функция `readPage`.

### Пришло «Worker молчит N часов»

Это написала суточная сверка с GitHub, значит Worker не просыпается. Запасная
рассылка уже включилась сама — скидки идут, но раз в сутки. Чинить:

```
cd worker && npx wrangler deploy --keep-vars
```

### Пума сменила вёрстку

Симптом: карточки перестали уходить, в логах «размеров нет» подряд у всех.
Опорные точки перечислены в шапке `src/puma.js`. Правится там и только там.

Проверять правку **не надо деплоить**: сохранить страницу товара в файл и
прогнать `node --test` — разборщики это чистые функции.

### Ничего не понятно

`npx wrangler rollback`, потом разбираться. Откат безопасен всегда.

## Важно: webhook и polling несовместимы

Пока webhook включён, `getUpdates` не работает — Telegram отдаёт 409. Значит:

- запуск бота на компе через polling (`scripts/run-local.bat`) **не получит
  команды**, пока webhook не снят;
- вернуться к polling: один раз открыть `.../deleteWebhook`;
- обратно на Worker — снова `setWebhook`.

## Кто может нажать /start

Отвечаем всем, подписка открытая. Нажавший попадает в KV (`sub:<chat_id>` с
именем и `@username`) и сразу начинает получать рассылку — её ведёт тот же
Worker, так что переносить никуда не надо. Суточная сверка забирает список к
себе в `data/puma.db` через `GET /subs` только ради запасного пути.

`/subs` и `/state` отвечают 403 без правильного `X-Subs-Token`, и так же если
`SUBS_TOKEN` вообще не задан.

## Почему карточки в /start не повторяются

Витрина — последние 20 отправленных карточек. Показываем 5, но не первые пять, а
пять подряд от случайного места с заворотом по кругу (`pickItems`). Нажал ещё
раз — увидел другие.

## Откуда берётся витрина

Из уже отправленных карточек в KV: там готовы и цвет, и размеры. **Ни одного
запроса в сеть на `/start`.** Раньше для этого собирался `data/latest.json`
отдельным проходом по ~22 страницам товаров каждый час — этого больше нет.
